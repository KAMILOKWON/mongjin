# JEV 임시 랭킹 봇 — parallel-v9

2026-09-20. 사용자가 선택한 범위는 **랭킹 봇 엔진 적용 + 로컬 검증**이다.
[제공받은 설계 원문](JEV-PARALLEL-DESIGN.md)을 기준으로 서버에 구현했다.
원문이 가리키는 기존 v3 및 로컬 대국 UI는 별도 `mongjin-arena` 프로젝트에 있으며 변경하지 않았다.
별도 판단 패널·재시도 UI·48판 기력 비교·모바일 출시는 이번 범위에 포함하지 않는다.

## 동작

- `ranked-bot-jev`, 표시 이름 `침착맨이할때까지`, 최초 Elo 1200. 재시작하거나 비활성화해도 기존 전적을 지우지 않는다.
- JEV는 이용자 점수와 관계없이 매칭 후보에 포함한다. 기존 봇은 기존 점수대 후보 규칙을 유지한다.
  후보 간 추첨은 기존 Elo 거리·최근 상대 가중치를 사용하므로 JEV와 점수 차이가 클수록 선택 확률은 낮다.
  직전 상대가 JEV면 연속 매칭하지 않으며, JEV 대국은 동시에 한 판만 허용한다.
  봇끼리 자동 대국하거나 인위적인 승리를 추가하지 않는다. 랭킹 상승에는 실제 이용자 대국이 필요하다.
- 전체 합법 수의 즉승·상대 다음 수 승리를 먼저 검사한다. 미완료 검사와 막힌 경로를 구분한다.
- 첫 API: 생존·차단·돌파·교환·전진·기본 담당의 Choice 6개와 Boolean 5개를 함께 요청한다.
  Boolean은 Vercel Evaluation API의 Noul 대응 형식이며, 낮은 확률을 이유로 역할을 끄지 않는다.
- 중복 수를 병합하고 제안 담당을 보존한다. 경로·공격 칸·보유 및 배치된 호위를 반영해 제안 후보를 탐색한다.
- 첫 여섯 Choice를 유지하면서 서로 다른 호위 후보를 턴 전체에서 최대 두 개까지 보충한다. 돌파 담당 분포에서 배치 수,
  차단 담당 분포에서 호위 행동을 각각 선택하고, `coverage` 출처를 명시한다. 확률을 합산하거나 최종 착수를 강제하지 않는다.
  최초 제안에 이미 호위가 있어도 다른 호위 대안을 남긴다. 즉패로 확인된 호위 수는 안전한 대안이 있는 경우 보충하지 않는다.
  판 위 호위와 대기 호위를 구분해 모델에 전달한다.
- 공통 4ply를 목표로 하고, 불안정 후보는 최대 6ply로 연장한다. 실제 완료 깊이와 방어 응수 검사 범위를 기록한다.
  강제승패는 필요한 응수가 모두 검증된 경우에만 확정한다. 부분 후보의 패배를 전역 강제패로 표시하지 않는다.
- 재제안 때문에 공통 깊이가 줄어도 기존 승패 증거를 `retainedProofs`에 보존한다.
  공통 깊이의 평가와 확정 증거의 원본 탐색·수순을 구분하며, 모순되는 확정 결과는 오류로 처리한다.
  v4~v8의 기존 판단 기록도 계속 재생할 수 있다. 종국 증거의 실제 마지막 결과와 왕 압박 예시의 합법성·다음 응수 안전성을 재생 검증한다.
- v9의 `mongjin-briefing-3`은 교대 턴·왕의 비포획·호위 배치 확장·포획된 호위의 영구 제거를 명시한다.
  좌표 JSON 대신 말 종류와 행동을 설명하는 후보 문장을 사용한다. 정적 경로는 다음 차례를 반영한 도달 시점 추정과 함께 전달한다.
  상대 호위의 왕 추격과 그 뒤의 안전한 대응 예시를 별도로 계산한다(1초·2만 노드, 후보당 최대 3예시).
  여기서 안전은 상대 다음 수의 종국 패배를 피한다는 뜻이며, 이후 전체 안전이나 승리를 의미하지 않는다.
  미완료 범위를 표시하고 이 자료로 후보를 강제 제외하거나 최종 선택을 덮어쓰지 않는다.
- 최종 API는 후보 중 Choice 하나를 선택한다. 종합 점수·BEST/LOWER 표시는 입력에서 제외하며 반환 ID를 그대로 적용한다.
  확정 즉승 또는 검증 뒤 단일 후보는 API를 생략하고 엔진 선택임을 기록한다. 재제안은 최대 한 번이다.
- 계산은 별도 프로세스에서 실행한다. 절대 마감 30초 안에 기록 저장·상태 해시·합법성을 확인한 뒤 착수한다.
  대국 종료·취소 시 작업을 중단하고 늦게 도착한 응답을 버린다. 240ply 제한을 둔다.
- API 오류·잘못된 응답·시간 초과·240ply 도달은 기존 랭킹 클라이언트에 오류를 알리고 **무효 종료**한다.
  판과 판단 기록은 보존하고 승패·Elo에 반영하지 않는다. 다른 AI가 대신 착수하지 않는다.
  사용자는 기존 매칭에서 새 대국을 시작할 수 있다. 같은 판에서 재시도하는 별도 UI는 구현하지 않았다.

[Vercel 모델 페이지](https://vercel.com/ai-gateway/models/jev)는 무료 프로모션 종료일을 2026-09-25로 안내한다.
시간대가 명시되지 않아 코드에서는 **한국 시간 9월 25일 00:00**에 중단하고 5분 전부터 새 매칭을 받지 않는다.
응답의 보고 비용이 정확히 0인지 확인한다. 누락·유료 비용·잘못된 응답은 실험을 중단한다.
비용 확인은 응답 이후이므로 첫 요청 과금을 사전에 보장하는 기능은 아니다. 활성화 전 무료 적용을 실호출로 확인해야 한다.
429·시간 초과는 60초 매칭 휴지기를 두고, 실패가 누적 3회면 서버 프로세스 내에서 중단한다.
즉시 중단하려면 `MONGJIN_JEV_ENABLED`를 제거하거나 `0`으로 바꾸고 서버를 재시작한다.

`/health`의 `jev`에 전략·만료 시각·매칭 허용·실패 횟수·중단 사유가 표시된다. 키는 노출하지 않는다.
로컬 검증 후 사용자가 `침착맨이할때까지` 닉네임으로 운영 배포를 승인했다. 이전 `403 customer_verification_required`는 최종 재확인에서 발생하지 않았고,
최초 배포 전 키로 실제 JEV 2단계 요청과 로컬 서버 착수까지 성공했다. 정상 응답으로 확인된 요청의 보고 비용은 0이었다.
9월 20일 추가 시범 대국 중 제공자의 429·503과 시간 초과도 발생했으며, 비용 메타데이터가 없는 실패 응답은 비용 0으로 확인했다고 보지 않는다.
다른 유료 제공자나 TypeSafe 직접 키로 자동 전환하지 않는다.

## 기록과 로컬 검증

일반 기보는 기존 JSON/MGN 형식을 유지한다. 별도 판단 기록에는 시작 스냅샷, 질문·응답,
역할·탈락 근거, 계산 깊이·시간·노드, 토큰·비용, 정책·규칙·프로토콜 버전, 적용 전후 해시를 보존한다.
PostgreSQL에서는 `mongjin_jev_turns`, 파일 모드에서는 프로필 파일 옆 `jev-decisions/`에 저장한다.
같은 턴의 쓰기를 직렬화해 늦은 저장이 최종 상태를 덮어쓰지 않게 한다. JSONL 내보내기와 manifest를 제공한다.

서버 디렉터리에서:

```sh
# 네트워크 없이 한 턴과 기록 검증
npx tsx verifyJev.ts --mock --out /tmp/jev-mock.jsonl
npx tsx verifyJev.ts --replay /tmp/jev-mock.jsonl

# 카드 인증·무료 적용 확인 후 실호출: 키 내용은 명령에 넣지 않는다
npx tsx verifyJev.ts --live --key-file /path/to/key.local --out /tmp/jev-live.jsonl

# 로컬 시범 대국: 기존 봇 1000/1400점, 흑백 교환 4판. 운영 프로필·Elo를 변경하지 않는다.
npx tsx benchJev.ts --live --key-file /path/to/key.local --matrix --side both --seed 20260920 --max-plies 100 --turn-pause-ms 5000 --outdir /tmp/jev-benchmark-new
# 로컬 기력 실험에서만 제한적으로 재개하려면 --transient-retries 2 추가; 기본은 오류 시 중단

# 서버 환경의 판단 기록 내보내기
npx tsx verifyJev.ts --export --out /tmp/jev-decisions.jsonl
```

검증 도구는 기존 출력 파일을 덮어쓰지 않는다. `--mock` 결과는 실제 JEV의 판단·기력·토큰·지연 측정값이 아니다.
재생 검사는 원래 이력, 후보 응수 수순의 합법성, 선택 출처, 적용 전후 해시를 확인한다.

필수 확인 명령(저장소 루트):

```sh
npm test -- --dir src --maxWorkers=1
npm test -- --dir bot --maxWorkers=1
npm test --prefix server -- --maxWorkers=1
npm run typecheck --prefix server
npm run build
```

PostgreSQL 검증에는 운영 DB와 분리한 `MONGJIN_TEST_DATABASE_URL`을 지정한다.
실제 WebSocket 서버·별도 계산 프로세스·합성 Gateway 응답으로 정상 한 수, 대기 중 항복,
API 503, 기보와 판단 저장, Elo 중복 반영 방지를 확인했다.
실제 Gateway를 연결한 Node 20.20.2 로컬 서버에서도 `JEV` 1200으로 매칭하여 첫 합법 수를 적용하고
저장된 `applied` 기록과 실제 보드의 해시가 같은지 검증했다.

v4 매칭 수정 시 검사: 공통 소스 80개 + bot 10개 + 서버 170개, **260개 테스트 통과**.
서버 170개에는 분리한 로컬 PostgreSQL 16 검사도 포함하며 Node 20.20.2에서 실행했다.
점수대 제한 해제 후 800·1500·1800·2400점의 JEV 후보 포함, 기존 봇 후보 보존,
비활성화·직전 상대 제외, 최소 후보 보충 및 후보 중복 방지를 검증했다.
최신 main의 `1등찍고접기` 봇을 함께 유지한 상태에서 서버 전체 검사를 다시 통과했다.
서버 타입 검사와 루트 프로덕션 빌드도 통과했다. 앱 화면·실기기는 이번 서버 변경에서 검증하지 않았다.

## 측정 범위와 남은 확인

[로컬 계산 측정 원본](jev-parallel-benchmark-20260920.json)은 Node 25.9.0, macOS arm64에서 얻었다.
API 시간은 포함하지 않으며 모두 개발 중 사용한 국면이다. 독립 기력 검증으로 해석하지 않는다.

| 국면 | 전체 합법 수 | 사실 준비 | 앞의 6후보 계산 | 공통 깊이 |
| --- | ---: | ---: | ---: | ---: |
| 초기판 | 6 | 8ms | 222ms | 4ply |
| 원본 20수 후 | 30 | 13ms | 2,596ms | 4ply |
| 원본 25수 후 | 23 | 13ms | 1,495ms | 4ply |

20수 후 정적 경로는 흑 5·백 11걸음으로 재현됐다. 원본 29수 전체를 재생하여 흑의 목표 도달을 확인했다.
25수 후 **전체 23후보**를 5초 예산으로 계산한 별도 측정은 공통 3ply에서 멈췄다.
이 측정만으로 전체 강제패를 확정하지 않는다. 단위 테스트는 원본 26번째 착수의 4ply 패배를 확인한다.
별도로 30초·100만 노드 상한을 둔 오프라인 검사에서는 84,507노드, 공통 4ply로 23후보 모두의 패배를 재현했다.
이 추가 검사의 예산을 실전 기본값으로 사용하지 않는다.
현재 시간·노드 예산은 임시 정책이다.

실제 API 초기판 단일 턴은 1,804ms, 입력 7,422·출력 826토큰, 보고 비용 0으로 완료했다.
실제 Gateway를 사용한 로컬 WebSocket 대국은 매칭부터 첫 `STATE` 및 기록 확인까지 1,493ms,
엔진 1,372ms, 공통 4ply, 입력 7,421·출력 826토큰, 보고 비용 0이었다.
두 실행 모두 JEV의 최종 ID `m_8_4_7_4`를 그대로 선택했고 기록 재생을 통과했다.
두 번의 초기판 측정만으로 p95 목표 달성이나 기력 향상을 주장하지 않는다.
운영 서버 부하·실제 대국 승률·랭킹 1위 도달 가능성은 아직 검증되지 않았다.

실호출 한 턴의 요청 형식·비용 0·지연·기록 재생 검증은 통과했다.
2026-09-20 운영 공개와 닉네임 변경의 명시적 승인을 받았다.
이번 변경은 서버 전용이며 사용자 요청에 따라 앱 버전을 유지했다.

## 모델링·전술 개선 검증

[개선 검증 기록](JEV-ENGINE-VALIDATION.md)에 개발 단계별 실제 승패와 중단, 회귀 검사, 배포 여부를 구분한다.
모델 설명 방식은 [TypeSafe Choice 문서](https://docs.typesafe.ai/primitives/choice)의 선택지 이름과 설명을 명확히 작성하라는 지침을 참고했다.
같은 요청의 역할 간 토론이나 모델의 내부 사고 과정은 가정하지 않는다.
